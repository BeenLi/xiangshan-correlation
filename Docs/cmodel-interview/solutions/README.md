# 参考答案讲解与追问要点

每题的完整代码在同目录 `NN_*.cpp`，`main()` 里的 `assert` 就是题目里的测试向量。
这里只写**关键设计点**、**容易错的地方**和**追问的答题要点**。追问没有唯一答案，下面是可以展开的骨架。

## 01 仲裁器

**关键点**

- 取最低位的 1：`x & (~x + 1)`（即 `x & -x`）得到独热码，再 `ctz` 得下标。RTL 里就是一个前缀或链。
- 轮询的标准写法是"双固定优先级"：`masked = req & ~((1 << ptr) - 1)`，
  `masked` 非 0 就在 `masked` 里取最低位，否则在 `req` 里取。硬件上是两个固定优先级仲裁器加一个选择器。
- 指针**只在真正授权时**更新为 `g + 1`；没有请求时不动。
- 包锁定：锁定期间 owner 没数据也不能放给别人，否则多拍包会被别人的数据插进来（交织）。
- DWRR：状态是 `ptr`、每人一个 `deficit`，再加一个"本次访问是否已加过 quantum"的标志。
  quantum 只在访问**开始**时加一次；授权后指针不动，下次调用接着发同一个请求者的包；
  额度不够发队头包时才移指针，余额留到下一轮；指针扫过没请求的人时把它的 deficit 清零。

**易错**：`1ULL << 64` 是未定义行为，所以 `n=64` 要单独处理；`peek` 和 `arbitrate` 要分开，11 题要用。
DWRR 常见错误：每次调用都加 quantum（应该每次访问只加一次）；授权后就移指针（变成每次访问只发一个包，退化成按包轮询）；
空闲时不清零 deficit（测试向量第 4、8 拍会对不上）。

**追问要点**

1. 见上。RTL：`grant = req & ~(req - 1)`；双仲裁器结构或 `{req, req} & ~mask` 后取最低位再折回。
2. "指向被授权者 + 1"公平：每个持续请求者最多等 n−1 次授权。"每拍 + 1"不会饿死但不公平：
   例如 n=4 只有 0、1 请求，ptr=2、3 时都回绕到 0，于是 0 拿到 3/4 的授权。
3. WRR：每个请求者一个计数器，被授权后计数减一，减到 0 才移动指针并重装权重；
   想要交织更均匀可以用平滑 WRR（每轮 `cur_i += w_i`，选最大者，再 `cur_g -= Σw`）。
4. 矩阵仲裁器用 N(N−1)/2 位记录"i 比 j 优先"，被授权者把自己那一行清零、那一列置 1，
   正好实现最近最少授权（LRG）。面积 O(N²)，N 大时换成轮询或分层仲裁。
5. 只在"授权被下游接受"时才更新指针（iSLIP 的规则），否则指针会同步，吞吐下降。见 11 题。
6. WRR 按包计数，包长的请求者拿到更多字节；DWRR 按包长扣额度，长期带宽正比于 quantum、与包长分布无关
   （测试向量里 0 号的包长是 2 号的 3 倍，字节数仍是 2:1）。空闲清零是为了不让请求者攒额度：
   否则它空闲很久后回来，可以连续发一大串，把别人的延迟拉长，短时间窗口内就不公平了。
7. 让 `quantum_i >= 最大包长`，每次访问至少能发一个包，一次决策就是 O(1)：
   硬件上先算 `eligible[i] = req[i] && len[i] <= deficit[i] + (新访问 ? quantum[i] : 0)`，
   再对 `eligible` 做一次轮询仲裁，一拍完成。quantum 小于最大包长时要么每拍只推进一步、中间出气泡，
   要么一次算出要补几轮额度。quantum 越大交织越粗，单个请求者一次能连发 quantum + 最大包长 − 1 个字节，延迟抖动变大。
8. 在包头那一拍仲裁并一次扣掉整包长度（包头带长度），然后像 C 一样锁定直到 last 拍；
   中间每拍只看 owner 有没有数据，不再算 deficit。也可以每拍扣 1，但要在包头先检查 `len <= deficit`，否则包会被截断在中间。

## 02 环形 FIFO 与定延迟队列

**关键点**

- 指针取值范围 `[0, 2N)`，存储下标用 `ptr % N`。`size = (wr − rd + 2N) % 2N`，满就是 `size == N`。
  N 是 2 的幂时 `% 2N` 就是丢掉高位，和 RTL 的 `log2(N)+1` 位指针一模一样。
- 延迟队列给每个元素存 `readyAt = now + L`。延迟固定所以时间戳单调，只看队头即可。
- 测试 B 里"先 pop 后 push"使得满队列在同一拍能腾一个位置再进一个；吞吐 = 容量 / 延迟 = 2/3。

**追问要点**

1. 方法一：牺牲一个槽，`(wr+1)%N == rd` 算满，有效容量 N−1；方法二：额外的 `full` 标志或计数器。
2. 允许"满时同拍 pop+push"等价于 `can_push = !full || pop`，
   RTL 里会让上游的 ready 组合依赖下游的 ready，路径变长；不允许的话，长期处于满状态的队列吞吐减半。
   模型里通过"一拍内先处理消费者、再处理生产者"实现前者；反过来则是后者。
3. 乱序完成：用以 `readyAt` 为键的小根堆；或者条目里放就绪位，按序退出（类似 ROB）。
4. `std::deque` 分块分配、迭代时多一次间接寻址；固定大小环形缓冲连续存储、零分配，
   在每拍要被访问上百万次的仿真器里差别明显。

## 03 Credit 流控

**关键点**

- 发送端只看本地 credit 计数器，所以接收缓冲永远不溢出（`simulate` 里每拍 `assert`）。
- 一个 credit 的往返：第 t 拍随 flit 发出 → 第 t+Lf 拍到达并（同拍）被消费、发回 →
  第 t+Lf+Lc 拍回到发送端并（同拍）可以再用。所以每个 credit 每 `RTT = Lf + Lc` 拍用一次，
  吞吐 = `min(1, B / RTT)`，满吞吐需要 `B ≥ Lf + Lc`。

**追问要点**

1. 每多一个"下一拍才能用"就多一拍 RTT：flit 到达后下一拍才能消费 → `Lf+Lc+1`；
   credit 到达后下一拍才能用 → 再 +1。一般地：**B ≥ 一个 credit 从被花掉到能再次被花掉的拍数**。
2. valid/ready 里 ready 要跨长线组合传回去，或者打一拍后在接收端补 RTT 深度的 skid buffer。
   credit 把"有没有空位"变成发送端本地的寄存器状态，时序友好；代价是缓冲必须覆盖 RTT，并且要有回程线。
3. 每个 VC 一份 credit 计数器，共享缓冲池时再加一个共享计数器（例如每个 VC 保留 1 个 + 共享池）。
4. credit 以 flit 或字节为单位。虫洞路由按 flit 发；虚切通（virtual cut-through）要求攒够整个包的 credit 才发。
5. 守恒不变量：`发送端 credits + 链路上的 flit + 接收缓冲占用 + 回程上的 credit == B`，每拍检查一次。

## 04 五级流水线

**关键点**

- 两阶段：先只读 `cur` 算所有 `fire[i]`，从 WB 往 IF 推 ready：`ready_in[i] = !cur[i] || fire[i]`。再一次性写 `nxt`。
- 每级的下一拍状态只有三种：上游进来、变空（走了没人补）、保持（没走）。
  `nxt[i] = fire[i-1] ? cur[i-1] : (fire[i] ? 空 : cur[i])`，flush 再覆盖成空。
- load-use 必须和**本拍开始时**的 EX 比较。第 4 拍 ID=2、EX=1(load) → ID 不走，EX 下一拍变成气泡。
- flush 在分支离开 EX 那拍：IF、ID 作废，本拍就从 target 取指，所以第 8 拍 IF=6，代价 2 个气泡（第 8 拍的 ID、EX）。
- 第 11、12 拍 MEM 忙：MEM 不走 → EX 的 7 也走不了 → 反压一路传上去（这时上游已空）。

**追问要点**

1. 单阶段从下往上更新时，处理 ID→EX 之前 EX 里的 load 已经被移到 MEM，看到的 EX 是空的，于是漏检 hazard。
   要么先拍快照，要么用两阶段。
2. 全局 stall：一根 stall 线广播到所有级，逻辑简单，但扇出大，气泡挤不掉。逐级握手：气泡能被挤掉、吞吐更好，
   代价是 ready 链长。假设场景：逐级握手下 ID 的指令会走进空的 EX；全局 stall 下原地不动。
3. skid buffer（两项）：
   ```
   ready_up  = !skid_valid                       // 寄存器输出，切断组合路径
   out_valid = main_valid
   每拍：
     if (main_valid && !ready_down && in_valid && ready_up)  → 数据存进 skid（skid_valid=1）
     if (ready_down) main ← skid_valid ? skid : in;  skid_valid ← 0
   ```
   上游看到的 ready 来自寄存器，下游 ready 拉低的那一拍上游已经发出的数据由 skid 接住，不丢、不重复。
4. 提前到 ID：比较器要放到 ID，并且需要前递到 ID，代价 1 拍，但 ID 的组合路径变长。
   停顿时也解析：解析和"离开 EX"解耦，分支一进 EX 就重定向，再记一个"已解析"标志防止重复冲刷。
5. 用序号（ROB 下标、全局序列号）比较新旧：冲掉所有比分支年轻的指令。BOOM 等用 branch mask：
   每条指令带一个位向量，标记它依赖哪些未解析的分支，误预测时按位广播清除。

## 05 DRAM bank 状态机

**关键点**

- 状态 + 时间戳：`ACTIVATING` 和 `PRECHARGING` 是"等计时器"的状态，`ACTIVE` 再用 `nextRd` 管 RD 间隔。
- 每拍"先计时转移，再发命令"，所以第 3 拍可以同时完成 ACTIVATING→ACTIVE 并发 RD。
- 分类必须在"第一次成为队头"时做；在入队时分类会错（请求 2 入队时行 5 是开着的，但不代表它是命中）。

**追问要点**

1. 第 6 拍：请求 2 第 6 拍才成为队头，tRAS 的约束 `0+6=6` 恰好也满足，两者同时到；
   第 15 拍：请求 4 第 15 拍成为队头，`9+6=15` 同样恰好满足。把 tRAS 改成 8，就能看到 PRE 被 tRAS 卡到第 8 拍。
   （真实器件还有 tRTP：RD 到 PRE 的最小间隔，本题没建模。）
2. 本例里 FR-FCFS 和 FCFS 结果相同：请求 4 第 10 拍才到，那时行 7 已经打开，没有可以提前的命中。
   如果请求 4 第 4 拍就到，FR-FCFS 会在第 7 拍先读它（行 5 命中），再关行去服务请求 2、3，它们各晚 2 拍。
   饿死：命中流一直来，冲突请求永远等不到；用年龄上限或连续命中次数上限兜底。
3. 关页适合随机访问、局部性差、多核交织访问的场景：冲突时省掉 PRE 的 tRP。
4. bank 内：tRCD、tRP、tRAS、tRTP、tWR。rank 内跨 bank：tRRD、tFAW。channel 级：命令总线每拍一条、数据总线占用、读写切换 tWTR/tRTW。
   结构上分 Channel → Rank → Bank 三层，每层管自己的时间戳，发命令前逐层检查。
5. 加一个 `REFRESHING` 状态：tREFI 到期时置"需要刷新"，等当前操作结束后预充所有 bank，发 REF，阻塞 tRFC。刷新优先级高于普通请求，但可以推迟若干次。
6. 时间戳写法在空闲时不需要每拍更新，可以直接算出下一个有事可做的周期并跳过去（事件驱动）；
   递减计数器必须每拍都 tick 一次。

## 06 组相联 Cache

**关键点**

- `set = (addr >> offBits) & (sets − 1)`，`tag = addr >> (offBits + idxBits)`；写回地址用 `((tag << idxBits) | set) << offBits` 拼回。
- 用全局访问计数器 `clock_` 作为 lastUse 实现真 LRU，最简单不出错。
- 写分配：写缺失时新行直接 `dirty = true`。
- sector cache 里"tag 命中但 sector 缺失"既不是命中也不是行缺失，要单独计数，而且**不换行**。

**追问要点**

1. 真 LRU 最少 ⌈log2(N!)⌉ 位，常见实现每路一个 log2(N) 位的年龄：8 路 24 位/组，16 路 64 位/组。
   tree-PLRU 只要 N−1 位：每个内部节点 1 位，指向"该淘汰的那一半"，访问时把路径上的位都指向另一边。
   不同的例子（4 路）：依次访问 A B C D，再访问 C、A。真 LRU 淘汰 B；tree-PLRU 根指向右半边，右半边的位指向 D，淘汰 D。
2. 写直达 + 写不分配适合写多读少、写后不读的流。GPU 各 SM 的 L1 之间没有硬件一致性，
   L2 才是一致性点，所以全局写一般直写到 L2，L1 不保留（或者只按 sector 作废）。
3. 命中延迟加在响应队列上；缺失走 07 题的 MSHR；填充和读共用数据阵列端口时要加端口仲裁；
   tag 和数据并行访问省延迟费功耗，串行访问反之（L2 常用串行）。
4. 一个 tag 管 128B，tag 面积是 32B 行的 1/4；需要时只搬 32B，不浪费带宽；
   同一行的其他 sector 之后访问时 tag 已经在了，命中率比 32B 行高。
5. VIPT 用虚拟地址的组号索引，组号位必须落在页内偏移里，否则同一物理地址可能映射到两个组（同义词问题）。
   所以组数 × 行大小 ≤ 页大小，想要更大的 L1 只能加相联度。

## 07 MSHR

**关键点**

- 查找顺序：命中 → 同行 MSHR（次级缺失，合并）→ 空闲 MSHR（初级缺失）→ 拒收。
- "先回填后请求"决定了请求 2 在第 10 拍直接命中、请求 5 在第 21 拍拿到 B 释放的 MSHR、请求 6 在第 22 拍命中。
- 拒收就是反压，上游按序阻塞重试，所以一个被卡住的请求会把后面的全堵住（请求 3 原本可以第 3 拍发）。

**追问要点**

1. 增大 target 数；拒收的请求进 replay 队列，后面的请求继续发（乱序接收，需要维护同地址顺序）；
   GPU 里常见做法是整条指令重放（replay），由 LD/ST 单元重发。
2. GPGPU-Sim 等模型按行（128B）分配 MSHR，表项里带 sector 掩码；对同一行不同 sector 的新缺失，
   可以合并进已有表项并补发缺的 sector，或者单独分配，取决于设计。面试时说清楚取舍即可。
3. 真实硬件响应端口每拍只能回一个（或固定几个），合并的 K 个 target 要排队回，最后一个多等 K−1 拍。
   在高合并度（同一行多个 warp 命中同一 MSHR）的负载下影响明显，模型里要加响应队列。
4. 向下发请求时带上 MSHR 编号，回填时按编号直接索引，不依赖返回顺序。
5. Little 定律：在途请求数 = 带宽 × 延迟。想每拍回填一行、延迟 400 拍，就要约 400 个在途行，
   这决定了 MSHR 数量，而能产生这么多独立缺失的 warp 数决定了占用率（occupancy）需求。

## 08 离散事件队列

**关键点**

- `std::set<Event*, Cmp>`，比较 `(when, pri, seq)`。`seq` 保证全序且唯一，`erase(e)` 就是 O(log n) 的 deschedule。
- 事件在 set 里的时候不能改它的 `when/pri/seq`，否则 set 的有序性被破坏；所以 `reschedule` = 先删再插。
- 执行前先清 `scheduled_`、再调回调，这样回调里才能重新调度自己。

**追问要点**

1. 同一 tick 里"内存把响应送回 CPU"和"CPU 时钟沿"谁先发生，决定 CPU 这一拍能不能看到数据。
   gem5 里 `CPU_Tick_Pri` 的数值比默认优先级大（执行更晚），保证同 tick 的其他事件先完成；统计、退出类事件优先级更低（更晚）。
2. 惰性删除：在事件上打 squashed 标志，弹出时跳过。坑：被取消的条目占内存；同一事件重新调度后堆里有新旧两份，
   要用版本号区分；事件对象被析构时堆里还留着指针（悬空）。
3. gem5 用的是有序的两级链表：外层按 (when, priority) 排序的"桶"，桶内是同时同优先级的事件。
   大部分事件都调度在不远的将来，插入点靠近表头，所以平均很快，也不需要堆的整体搬移。
4. 每个模块在"有活干"时调度自己的下一拍，空闲时不调度，被别人唤醒时（例如收到请求）再调度。
   适合：存储控制器、互连等经常空闲的模块；不适合：每拍都在动的核流水线（事件开销比直接 tick 更大）。
5. 每个线程一个事件队列，按时间片（quantum）同步：所有队列跑到同一个时间边界再交换跨队列消息，
   quantum 要小于跨队列通信的最小延迟才能保证正确性。gem5 的多队列模式就是这样做的。

## 09 Warp 调度器与记分板

**关键点**

- 记分板用"寄存器可用的周期"，检查 RAW（源）和 WAW（目的）。第 t 拍发射、延迟 L，就写 `regReadyAt[dst] = t + L`。
- LRR 每拍从 `last + 1` 开始；GTO 先试 `last`，再从 0 找最老的。
- 第 2、3 拍两个 warp 都在等 load，空发射：这就是"warp 数不够掩盖延迟"的样子。

**追问要点**

1. GTO 让一个 warp 尽量连着跑，它的工作集在 L1 里保持热，减少 warp 间互相踢；
   LRR 把所有 warp 拉到同一进度，大量 warp 同时缺失，L1 容易抖动。warp 之间共享数据、或频繁 barrier 同步的负载，LRR 可能更好。
2. 两级调度：只在一个小的活跃 warp 集合里调度，遇到长延迟操作的 warp 移到等待池。
   一是调度逻辑变小；二是让 warp 处于不同阶段，避免所有 warp 同时跑到长延迟操作上一起停。
3. 1 bit 只知道"在飞"，写回时清位，需要写回事件；时间戳只适合固定延迟。load 这种可变延迟的，
   发射时置位、数据回来时清位，所以模型里要有写回通知。
4. 公开的逆向分析（例如对 Volta/Turing 指令编码的研究）显示：定长延迟靠编译器在指令里写 stall 周期数，
   变长延迟靠少量依赖屏障计数器。模型里体现为：warp 发射后 N 拍内不可调度；变长指令在完成时减屏障计数，依赖者等屏障清零。
5. 发射后先进操作数收集器（operand collector），按寄存器堆 bank 仲裁读端口，操作数凑齐后再派发到执行单元。
   中间多了 collector 单元数量和 bank 冲突两种结构冒险。

## 10 合并访存与 bank conflict

**关键点**

- `map<行号, sector 掩码>`：行数 = map 大小，sector 数 = 掩码 popcount 之和。
- 共享内存按 bank 放 `set<字地址>`，同一个字只算一次（广播）。周期 = 最大集合大小。

**追问要点**

1. 字下标 `i × 33`，因为 `33 ≡ 1 (mod 32)`，所以 bank = `i mod 32`，32 个线程正好落在 32 个 bank。
   转置时按列读 `tile[i][c]`，没有填充时字下标步长是 32，全落在同一个 bank，32 路冲突；多一列就把步长变成 33。
2. 常见的说法是：8B 访问时一个 warp 分成两个半 warp 阶段处理，16B 访问分成四个阶段，每阶段最多 128B，冲突只在同一阶段内统计。
   具体规则随架构变化，面试时说清楚"按 128B 每阶段"的思路即可。
3. compute 1.0/1.1 要求半 warp 内线程顺序对齐访问，否则拆成 16 次；1.2/1.3 放宽为按 32/64/128B 段合并；
   Fermi 起全局访问经过 L1，以 128B 行为单位；之后 L1/L2 都采用 32B sector，和 DRAM 的访问粒度对齐，未对齐和稀疏访问的浪费更少。
4. 在 LD/ST 单元地址生成之后、L1 tag 查询之前。tag 每拍能处理的行数有限，32 行的发散访问要占用 L1 tag 32 拍左右，
   模型里体现为合并结果排成一个请求队列，每拍出一个（或几个）。
5. 全局原子在 L2 的原子单元执行，同址原子会被串行化（有的架构在 warp 内先归约再发）；
   共享内存原子同址不能像普通读那样广播，必须串行。

## 11 Crossbar

**关键点**

- 两阶段：所有输出先根据本拍开始时的状态授权，再统一出队，避免同一个输入在一拍里送出两个包。
- FIFO 版：c 去 out0 排队时，d/e/f 被堵住，out1 在第 0、1 拍空转（HOL 阻塞）。
- VOQ + iSLIP：只有 accept 的对才更新指针。第 0 拍 out1 只有 in1 请求，in1 只收到 out1 的授权，直接匹配，d 第 0 拍就走了。
- 反压：输出不 ready 就不参加授权。FIFO 版里 out0 的停顿把 in1 的队头 c 也拖住，进而把去 out1 的 d/e/f 全拖后；VOQ 版 out1 不受影响。

**追问要点**

1. 大 N、均匀独立到达时，输入排队 crossbar 饱和吞吐趋于 `2 − √2 ≈ 58.6%`（Karol 等，1987）。
   原因是队头冲突：多个队头争同一个输出时只有一个能走，其余整个队列都被堵住。
2. 第 1 拍的 `{in1→out0}` 已经是一个极大匹配（maximal）：in0 只想去 out0，out0 已被占；out1 只有 in1 请求，in1 已被占。
   iSLIP 多轮迭代只能收敛到极大匹配，找不到这里的最大匹配（maximum）`{in0→out0, in1→out1}`。
   多轮时只在第一轮更新指针，否则会破坏"不饿死"的性质。
3. 授权就更新（RRM 的做法）会让所有输出的指针同步到同一个输入，大家授权同一个人、只有一个被接受，吞吐上不去；
   只在 accept 时更新，指针会自然错开（去同步），均匀流量下单轮就能接近 100%。
4. 共享缓冲加按输出的链表；每个输入只保留少量 VOQ，按哈希分配输出；或者输出排队并给交换结构加速比（例如 2 倍速）。
5. 每个输出维护下游缓冲的 credit：credit > 0 才参与授权，授权时减一，下游消费后经过回程延迟加回。
   `ready(out, t)` 换成 `credits[out] > 0`，再加一个 03 题那样的 credit 回程延迟队列。
